# ADR-004: Один Redis, Cache Aside

- Status: Accepted
- Date: 2026-10-22
- Deciders: команда «Мобильный мир»

## Context

`GET /{collection}/users` в `app.py` спит одну секунду. Декоратор `@cache(expire=60)` работает только при `REDIS_URL`; на стенде из ADR-001 переменной нет, и каждый список ждёт секунду. Третий шаг задания 1 копирует схему реплик и добавляет один `redis`.

Стрелки: `pymongo-api` → `redis` (попадание в кеш и запись ответа) и `pymongo-api` → `mongos_router` (промах и любая запись). Redis к MongoDB не подключаем. Шарды, реплики и ключ `name` из ADR-002 и ADR-003 не меняются.

Один инстанс и 60 секунд — не одна настройка. Число узлов не делает ответ свежее: второй Redis хранил бы ту же копию.

## Decision

**Cache Aside, один инстанс.** При `REDIS_URL` список `GET /{collection}/users` сначала смотрит Redis. Промах — приложение читает MongoDB через `mongos_router` и само кладёт ответ в Redis. Запись документа и любой запрос не из этого списка идут в `mongos_router`, минуя кеш как источник данных.

Один инстанс, потому что задание 1 рисует один `redis`, а задание 4 даёт один `REDIS_URL`. Кластер нужен, когда не хватает памяти или отказоустойчивости кеша, а не когда пугает срок жизни ключа.

**Свежесть держит сброс ключа, не число узлов.** `expire=60` в текущем `app.py` — срок жизни ключа в коде. Cache Aside делает иначе: `POST` удаляет ключ списка, следующий `GET` читает MongoDB и кладёт новый ответ. В примере урока ключ живёт 120 секунд и всё равно сбрасывается на записи.

Так и фиксируем. Пока записи не было, старый список можно отдавать из кеша. После `POST /{collection}/users` ключ этого списка удаляется: 60 секунд устаревания после записи нет. Сам `expire` в приложении в этом задании не меняем, здесь схемы и ADR. Сброс ключа на `POST` — обязательный шаг, когда дойдём до кеша в коде. Без сброса окно в 60 секунд остаётся, и это решение мы не принимаем.

## Alternatives considered

- Read replica разгружает чтение базы, но не убирает `sleep(1)` на этом эндпоинте. Повтор быстрее 100 мс в задании 4 даёт попадание в кеш. Откуда читать реплику — задание 9.
- Redis Cluster не сокращает окно устаревания. Задание просит один инстанс. Второй узел хранил бы ту же копию, пока ключ не сброшен.

## Consequences

- Positive: повторный список не ходит в MongoDB и не ждёт секунду, пока ключ жив. После записи через этот API следующий список берётся из базы.
- Negative: сброс ключа покрывает только запись через этот API. Первый запрос после сброса всё равно бьёт в базу и снова ждёт `sleep(1)`. Один Redis — точка отказа пути кеша: упал он, пропадает ускорение, данные MongoDB остаются. Кеш полезен, когда один и тот же ответ читают часто. На низкой нагрузке он только усложняет систему.
- Follow-up: в коде кеша удалять ключ списка на `POST /{collection}/users`. `expire=60` в этом задании не трогаем. Consul, API Gateway и CDN — задания 5 и 6, в эту схему не входят.
