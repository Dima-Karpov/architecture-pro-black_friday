# ADR-008: Горячие шарды

- Status: Accepted
- Date: 2026-10-25
- Deciders: команда «Мобильный мир»

## Context

Задание 8. Категория «Электроника» перегрузила один шард: 70% запросов шло на эти товары. Следующая популярная категория даёт тот же признак, когда её доля достигает того же порога.

Ключ `shop.products` принят в [ADR-006](0006-products-shard-key.md): хэш `_id`. Категория как ключ отклонена там же. Балансировщик равняет объём коллекции. Доля запросов от числа байт не зависит: данные ровные, а операции сидят на одном шарде.

Стенд тот же, что в ADR-002: два шарда, маршрутизирует `mongos`. Схемы C4 задания 7 не меняются. Отдельного экрана метрик на стенде нет.

## Decision

**Горячий шард определяем двумя числами. Ключ `products` оставляем хэш `_id`.**

Объём собирает балансировщик на primary `configSrv`. Смотрим с `mongos_router`: `balancerCompliant`, `getShardDistribution` (`data`, `docs`, `chunks`) и `stats().shards[].size` в байтах. Коллекции: `shop.products`, `shop.orders`, `shop.carts`.

Операции и задержку снимаем в `mongosh` на primary шарда. На стенде это сначала `shard1-1` и `shard2-1`. Перед снятием читаем `db.hello().primary`. Окно 60 секунд, в расчёт идёт разница `opcounters` и `opLatencies`. Категорию запроса читаем из `system.profile` на том же primary, поле `command.filter.category`, тоже за 60 секунд при `setProfilingLevel(2)`.

Пороги:

- Доля операций шарда `(Δquery + Δupdate + Δgetmore)` / сумма двух шардов **≥ 0,70**. Число из задания. Значение `category` в формуле нет.
- Разница `size` коллекции **≥ 384 МБ** и `balancerCompliant: false`. 384 МБ — это 3 × чанк 128 МБ, порог, с которого балансировщик начинает перенос.
- Доля операций ≥ 0,70 при разнице `size` < 384 МБ — жар запросов. `moveChunk` в этом случае перевозит жар.
- Доля одного значения `category` среди записей `shop.products` в профилировщике **≥ 0,70**. Сегодня это может быть «Электроника».

`moveChunk` запускаем, когда разница `size` уже ≥ 384 МБ, а `balancerCompliant` остаётся `false`. Окно переноса 01:00–05:00. Повтор каталога горячей категории и карточки товара закрываем Cache Aside, тот же приём, что в [ADR-004](0004-redis.md).

Команды и поля — в [архитектурном документе](../07-10.md#задание-8-горячие-шарды).

## Alternatives considered

- Ключ `products` по категории. Мало значений, следующая категория с долей ≥ 0,70 снова сядет на один шард. Уже отклонено в ADR-006.
- `moveChunk` при доле операций ≥ 0,70 и разнице `size` < 384 МБ. Жар переезжает вместе с чанком. Один `_id` лежит в одном чанке целиком.
- Новый шард в пик распродажи. Балансировщик начинает массовый перенос. Добавление шарда — задание 10.

## Consequences

- Positive: по доле операций и разнице `size` видно, греют шард запросы или объём. Порог категории один для любого значения поля.
- Negative: горячий товар — один документ, перенос чанка его не размазывает. Профилировщик на уровне 2 включён только на 60 секунд. На стенде Cache Aside закрывает список `GET /{collection}/users`; для `shop.products` это тот же приём, не отдельный экран.
- Follow-up: чтение с primary или secondary — задание 9. Добавление шарда — задание 10.
